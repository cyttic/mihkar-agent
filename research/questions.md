Question 1: Is developers' trust in AI related to how much of its code they check?
Hypothesis 1: Developers who trust AI more check less of its code. Null hypothesis: developers who trust AI more do not check less of its code.
Definitions: developers are professional developers in Israel (paid, at least one year of experience) who use AI code assistants. Trust is a score on a trust questionnaire. "Check" means reading the code line by line or running tests on it before merging, reported as a percentage of the AI code they receive.

Question 2: Do reviewers report a different number of defects when code is labelled as AI-generated?
Hypothesis 2: Reviewers report more defects when the code is labelled as AI-generated. Null hypothesis: the label does not increase the number of defects reported.
Definitions: reviewers are professional developers. All reviewers get the same code; half of them, chosen at random, see the label, and the other half see no label. Reviewers are not told what is being tested. A reported defect is a review comment that points to a bug or a security problem, classified by two raters independently, who do not know which group the comment came from.

Question 3: Is AI-written web code more or less accessible than code written by developers?
Hypothesis 3: AI-written web code has more accessibility violations than developer-written code. Null hypothesis: AI-written web code does not have more accessibility violations than developer-written code.
Definitions: web code means web forms built from the same public specification, one form challenge on the Frontend Mentor website. AI-written forms are generated by AI code assistants from that specification. Developer-written forms are solutions to the same challenge that developers published on GitHub before 21 June 2022, the date GitHub Copilot became available to all developers, so they were very likely written without AI. Accessibility is measured by the number of WCAG 2.1 AA violations found by an automated checker, per form.

Our constraints:
- This is a research proposal. We plan the study but do not run it in this course. The constraints below describe the conditions the study would have if it were run.
- Access: we have no access to any company's internal code, code reviews or developers. We can reach developers through our personal networks, LinkedIn and Israeli developer groups online. We can use public data, such as public GitHub repositories.
- Participants: we expect about 30 to 60 developers to answer an online questionnaire, and about 20 to 40 developers to take part in a short online task (about 20 minutes each). We cannot pay participants.
- Time: one semester. About 5 weeks for data collection.
- Ethics: any study with human participants needs approval from the university ethics committee. Question 2 does not tell reviewers what is being tested, so it needs a debriefing at the end.
- Floor 2: all three questions and hypotheses passed floor 2 on 2026-11-08 (question 3 rechecked after its definition changed).
- Most important goal: we have not decided. Explain what each strategy gains and pays for each question.
