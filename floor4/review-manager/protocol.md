# Review protocol — trust, fairness and accessibility in AI-written code

Version 1, 2026-11-14. Status: **approved by the group on 2026-11-14.**
Type of review: a small systematic literature review (session 4, slide 23), one review question per research question.
Written before any search (Kitchenham & Charters 2007: the protocol comes before the search, so the findings do not set the rules).

## 1. Background
Our proposal has three research questions (see the research questions file): RQ1 trust in AI and checking AI code,
RQ2 the effect of an "AI-generated" label on code review, RQ3 the accessibility of AI-written web forms.
The review must show what is already known, where the gap is, why our questions are new, and which measures and
tools others used (session 4, slide 17). For RQ2 it must also justify the direction of our hypothesis
(more defects with the label): two known effects predict opposite directions (automation bias: trusting the
machine, so fewer comments; algorithm aversion: distrusting the machine, so more comments).

## 2. Review questions and PICOC
The review questions are broader than our research questions, so close studies are not missed (slide 25).

| | Review question | Population | Intervention | Comparison | Outcome | Context |
|---|---|---|---|---|---|---|
| RV1 (RQ1) | What does empirical research report on how developers' trust in AI code assistants relates to how they check AI-generated code? | Software developers | Using an AI code assistant based on a large language model (LLM) | Different levels of trust; or no comparison | Checking behaviour: reading, testing, reviewing or accepting AI code; trust measures | Industry or academia; any task size |
| RV2 (RQ2) | What does empirical research report on how believing that code is AI-generated changes how people review or evaluate it? | Developers, reviewers or students who review or rate code | A label or belief that the code was written by AI | The same code with no label, or labelled as human-written | Defects found, review comments, ratings, acceptance | Code review, grading or rating tasks |
| RV3 (RQ3) | What does empirical research report on the accessibility of web or user-interface code generated by AI, compared to code written by people? | Web or UI code (forms, pages, components) | Code generated by an LLM-based assistant | Code written by developers; or no comparison | Accessibility violations (WCAG), measured automatically or by experts | Any web technology |

`("AI-generated code" OR "LLM-generated code" OR "AI authorship" OR "machine-generated code") AND ("code review" OR evaluation OR rating) AND (bias OR perception OR "algorithm aversion" OR "automation bias")`

`("large language model" OR "AI-generated" OR "GitHub Copilot" OR ChatGPT) AND (web OR "user interface" OR HTML OR "front-end") AND (accessibility OR WCAG OR a11y)`

### Pilot (before the real search)
Run each string in one database. Before the pilot, each member writes down one or two papers they already know for
that question. If a known paper is missing from the results, add the missing synonym or narrow the string.
Record the final string and the date here (version 2 of this protocol).

### Snowballing
After the database search: backward (reference lists) and forward (who cites the paper, in Google Scholar) from
every included paper (Wohlin 2014). A new paper goes through the same criteria. Stop when a full round, backward and
forward, adds no new paper.

### Grey literature
Decided with the seven questions of Garousi et al. (2019, Table 4). One or more "yes" suggests including grey literature.
- RV3: yes (practitioners write a lot about accessibility of AI-generated front-end code, and the formal literature is small). Include grey literature for RV3 only: tool documentation and reports, blog posts by known accessibility organizations. Each grey source is checked for: who wrote it, the method, the date, and objectivity.
- RV1, RV2: no grey literature in version 1.

## 4. Selection criteria
Every criterion is a yes/no question.

| Code | Inclusion criterion |
|---|---|
| I1 | Empirical study that reports data (experiment, survey, case study, mining study, benchmark). |
| I2 | The AI tool is based on a large language model (RV1, RV3), or the study manipulates or measures the belief that code is AI-written (RV2). |
| I3 | The participants are developers, reviewers or programming students, or the material is source code. |
| I4 | Reports at least one outcome named in the PICOC table for that review question. |
| I5 | Published from 2021 on, in English. Peer-reviewed paper, or arXiv preprint marked as such. |

| Code | Exclusion criterion |
|---|---|
| E1 | Opinion paper, editorial or position paper with no data. |
| E2 | The tool is not based on an LLM (for example, rule-based code completion). |
| E3 | The same study published twice: keep the fuller version only. |
| E4 | The full text cannot be obtained. |
| E5 | Fewer than 4 pages (abstract, poster), unless it is the only report of a study. |

Note for RV2: studies on automation bias or algorithm aversion outside software (before 2021 or not about code) are
**background**, not included studies. They are listed separately and used only to justify the direction of H2.

## 5. Selection procedure
1. Remove duplicates.
2. Title and abstract: when in doubt, keep.
3. Full text: decide by the criteria. Record the reason and the criterion code for every excluded paper.
4. Calibration first: two members screen the same 10 papers independently, then discuss every disagreement. Many disagreements mean a criterion is unclear: fix it here, before screening the rest.
5. Compare our own screening of a sample with the decisions of floor 4 (session 4, slide 32).

## 6. Quality assessment
The same three questions for every included paper: Is the research question defined? Does the method fit the question? Are the limitations reported?

## 7. Data extraction
One row per paper: paper · research question · strategy (the eight strategies, session 3) · participants or material · main finding · limitation (built-in or accidental) · measures and tools used (for our own design).

## 8. Synthesis
Group the rows by question, strategy and finding into three groups: what is known, where studies disagree, what is
missing. The gap is claimed from the table, and every claim about a gap is checked against real papers.

## 9. Verification of every source
Before any source enters the proposal: search the exact title, compare authors, year and venue, open the DOI, and find
the claim in the paper itself. Status: verified, partly verified or not found. A source that is not verified does not
enter the proposal.

## 10. Dissemination and schedule
The review becomes the literature chapter of the proposal. Pilot and final strings: week 1. Search and screening:
weeks 2–3. Extraction, synthesis and verification: week 4. Presented at the first control meeting (after session 6).
